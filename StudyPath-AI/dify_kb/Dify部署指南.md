# StudyPath · Dify 云端部署指南

## 目标
把已验证的 RAG 能力套进 Dify 可视化壳，做成一个可分享的在线对话 Demo：打开链接即可提问，
答案基于同一套三库知识库。

## 前置
- dify.ai 账号
- 阿里云 DashScope API Key（现有，复用 StudyPath 的 key：qwen-plus + text-embedding-v3）

## 步骤
1. 注册登录 dify.ai，进入控制台。
2. 配置模型供应商（Dify 0.2.9 直接内置「通义」插件，比 OpenAI 兼容模式更简单）：
   - 设置 → 模型供应商 → 找到「**通义**」（带阿里云标识）→ 点右侧「**配置**」或「**+ 添加模型**」
   - **加 LLM**：模型类型选「LLM」→ 模型名选 `qwen-plus`（下拉里通常有，也可手输）→ API Key 填你的 DashScope Key（sk- 开头）→ 保存
   - **加 Embedding**：再点「+ 添加模型」→ 类型选「TEXT EMBEDDING」→ 模型名 `text-embedding-v3` → 同 Key → 保存
   - （可选）类型「RERANK」也加一个 `gte-rerank` 之类，可显著提升检索精度
   - 注意：Dify 插件已默认填好 API Base = `dashscope.aliyuncs.com`，无需手填
   - 不再走 OpenAI 兼容模式——Dify 原生通义插件已内置，你当前截图就是这条路 ✅
3. 创建知识库：
   - 知识库 → 创建 → 上传文件，选本目录下三个 .md
   - 分段：默认按 Markdown 标题（已用 `##` 分段），TopK 建议 4-6，Score 阈值 0.5 左右
   - 索引：高质量（用上面配的 text-embedding-v3）
   - 等待向量化完成
4. 创建应用（**选 Chatflow，不是聊天助手**）：
   - 工作室 → 创建空白应用 → 类型选「**Chatflow**」→ 命名「StudyPath 留学规划助手」→ 创建
   - **节点搭建（关键）**：
     - 拖 3 个「**知识检索**」节点，每个都从「开始」节点拉线出来（并联），分别绑定：
       - 知识检索·院校 → StudyPath-院校项目库，查询变量 `sys.query`
       - 知识检索·案例 → StudyPath-录取案例库，查询变量 `sys.query`
       - 知识检索·文书 → StudyPath-文书范例库，查询变量 `sys.query`
       - 每个节点 TopK=3
     - 拖 1 个「**LLM**」节点，把三个检索节点的输出线都连到它；模型 `qwen-plus`，记忆窗口开 5-10 轮
     - 拖 1 个「**直接回复 / 结束**」节点，连在 LLM 后，输出选 LLM 文本
   - **✅ 上下文自动注入机制（已验证 2026-08-18 跑通）**：在 Dify Chatflow 中，**只要把知识检索节点直接连到 LLM 节点，检索结果会自动作为上下文注入 LLM，无需任何手动配置**。LLM 节点「上下文」那个下拉是给"额外再加一段"用的（如要再手动塞变量），不是必填。Prompt 编辑器变量面板不显示上游节点输出也不影响自动注入。
     所以**最简结构就是**：开始 → 3 知识检索并联 → LLM → 直接回复，无需加模板转换节点。
   - LLM 节点配置：
     - 模型：`qwen-plus`
     - 记忆窗口：5-10 轮（开启多轮对话）
     - 「上下文」区域：留空即可（已自动注入）
     - USER 提示词结构（与线上部署版一致）：固定开头 + 三路检索结果占位 + 用户问题变量 + 规则列表。开头写「你是 StudyPath AI 留学申请规划助手，请严格基于下方三路检索资料回答用户问题。」，随后依次放三个检索结果变量的占位、`{{#sys.query#}}`（从变量面板选「开始/sys.query」插入），最后是规则。
     规则（写在 LLM 的 USER 提示词里，2026-10-13 与线上部署版逐条核对一致）：
     1. 当用户问【申请要求/录取门槛/GPA/托福/雅思/GRE/截止日期】→ 引用「院校库检索结果」
     2. 当用户问【我背景够不够 / 录取可能性 / 类似案例】→ 引用「录取案例库检索结果」
     3. 当用户问【SOP/PS/CV/简历/文书模板/范例链接/写作指导】→ 必须且只能引用「文书库检索结果」
     4. 其他问题按相关性综合引用三库；资料不足时如实说"该信息未在知识库覆盖"，建议去官网核实
     5. 用 ### 小标题 + - 列表呈现
     6. 末尾附 [资料N] 引用（对应 source_url）
     7. 面向具体申请者说话，像顾问给建议一样直接给结论；不要写"在数字化浪潮席卷全球的今天"这类宏观铺垫式开场，也不要写成泛泛而谈的通用说明文
     8. 不要向用户展示知识库或内部模块的名称（如"院校库""录取案例库""文书库"），也不要暴露内部工作流程；一律改用「申请要求」「录取案例」「文书范例」这类业务说法
     9. 判断"最新/当前申请季"一律以系统当前日期为锚，不得把知识库里出现的最大年份当作"最新"；截止日期已早于当前日期的记录属于往季，不得称作"最新"，也不得写成待办；知识库未覆盖当前申请季时，如实说明"知识库收录为往季数据，最新截止日请以官网为准"
     （1–3 是**三库路由分流**，对应本地主链 LangGraph 的 supervisor 路由；4–6 是事实与格式；7 是语体；8 是防内部信息外泄；9 是时间口径——8、9 都是主链已有、Dify 侧原来缺的约束。）
   - 调试：右上「运行」输入测试题，确认三个检索节点各自召回 + LLM 跨库汇总；再追问一句验证多轮记忆（如"那 CMU 的 GPA 要求多少？"）
5. 调试：输入测试问题，确认召回片段正确、回答带 source_url
6. 发布：点发布 → 获得公开 URL，发给老师/评委

## Prompt 模板（贴到应用编排的「指令」里）
```
你是 StudyPath 留学规划助手。严格基于【知识库】内容回答用户关于留学申请的问题。
规则：
1. 只用知识库里的事实，绝不编造院校/排名/分数/录取案例。
2. 知识库不足时如实说明，并建议补充哪类数据。
3. 面向具体申请者说话，像顾问给建议一样直接给结论；不要写"在数字化浪潮席卷全球的今天"这类宏观铺垫式开场，也不要写成泛泛而谈的通用说明文。
4. 用中文、条理清晰，用 ### 小标题 + - 列表呈现。
5. 每条事实附上来源链接（source_url / 来源）。
6. 覆盖三类问题：院校推荐、背景匹配评估、文书范例。
```

> 注：上面这段是**应用级「指令」（system 角色）**，定角色与总原则；LLM 节点 USER 提示词里的 6+1 条定的是**三库路由与输出格式**（见上一节）。两处不是同一处、互不冲突，可同时存在。

## 与本地主链的口径对齐（语体同步）

本地主链（`rag/qa.py` 单链、`rag/agents.py` 三个 worker + 整合器）在实验①之后加了一条语体规则：
「面向具体申请者说话、像顾问给建议一样直接给结论，不写宏观铺垫式开场」。
Dify 这条链路是对外出口，提示词必须跟主链共用同一套规则，否则同一个项目从两个入口问会得到两种腔调。

同步范围（改哪儿、为什么）：

| 环节 | 是否改 | 原因 |
| --- | --- | --- |
| Dify LLM 节点提示词 | **要改** | 它是这条链唯一生成文字的地方，追加第 7–9 条（语体 + 防内部信息外泄 + 时间口径）即可齐 |
| 事实铁律（不编造 / 不足则说明 / 附来源） | 已一致 | 第 4–6 条本就覆盖，无需改动 |
| N8N 工作流 | **不用改** | N8N 没有 LLM 节点，它只是 `HTTP Request` 调 Dify API → `Edit Fields` 提取 answer → 推飞书。推给群里的文字就是 Dify 的返回，改 Dify 自动改到了飞书 |

⚠️ 「运行独立」和「口径统一」是两件事：Dify 在云端跑、主链在本地跑，运行时拓扑各自独立（PPT 第 11 页的说法）；但对外交付给用户的回答应当出自同一个顾问口径。

操作路径（逐层）：登录 dify.ai → 右上角进入 **工作室** → 打开应用 **StudyPath 留学规划助手** → 右上 **编排** → 画布上点 **LLM** 节点 → 右侧面板 **USER 提示词** 框 → 在**规则列表的最后追加**下面这一条 → 右上 **发布** → **更新**。

要追加的规则（可直接粘贴；第 7 条你已贴过，从第 8 条继续贴）：

```
8. 不要向用户展示知识库或内部模块的名称（如"院校库""录取案例库""文书库"），也不要暴露内部工作流程；一律改用「申请要求」「录取案例」「文书范例」这类业务说法。
9. 判断"最新/当前申请季"一律以系统当前日期为锚，不得把知识库里出现的最大年份当作"最新"；截止日期已早于当前日期的记录属于往季，不得称作"最新"，也不得写成待办；知识库未覆盖当前申请季时，如实说明"知识库收录为往季数据，最新截止日请以官网为准"。
```

⚠️ 核对线上部署版（面板顶部显示「已发布 2 个月前」）时，USER 提示词的**实际结构**是「三路检索结果 → 用户问题 `{{#sys.query#}}` → **6 条规则**」：前 3 条是三库路由分流（申请要求/门槛/截止日→院校库；背景与案例→案例库；文书→文书库），第 4–6 条是事实与格式。**上一节的模板已按这个实际结构对齐**，不再另设一套。
**所以一律"末尾追加第 7–9 条、不插中间、不给已有规则重新编号"**——插到中间会打乱路由顺序，把分流逻辑切断。

## 测试题（验证用）
- 我想申请美国 CS 硕士，GPA 3.5 托福 100，推荐哪些学校？需要准备什么文书？
- 给我一个 MIT 计算机 SOP 的真实范例链接。
- 双非 GPA3.0 托福90 能申到什么档次美国 CS 硕士？
- 帝国理工和 UCL 哪个更稳（GPA3.5 雅思7.0）？

## 注意
- 数据与 StudyPath 本地版（rag/）同源（同一份 xlsx），保证答辩口径一致。
- Dify Chatflow 版用 3 个独立知识检索节点**复刻了本地多智能体的「三库隔离检索 + 跨库汇总」架构**（可视化等价物），与本地 LangGraph 版形成"代码 + 拖拽"双对照，答辩叙事最亮。
- 模型走阿里云 API（qwen-plus + text-embedding-v3），数据上传到 Dify 云端（实际托管在 `udify.app` 子域）；本库均为公开 source_url，无敏感信息。
- 免费版限制：每次只能上传 1 个知识库文件（需分 3 次建库），但 Chatflow 关联多个库、调多智能体无限制。
