# StudyPath 项目需求与功能说明

>   基于代码与数据事实整理，无虚构数据。

---

## 一、背景与价值

### 1.1 痛点

在我们留学申请过程中，学生需要同时处理大量的分散信息：

- **院校信息分散**：各项目官网格式不一，GPA、语言、GRE、截止日期、学费、偏好背景等关键字段散落在不同页面，人工整理耗时。
- **录取案例难对标**：不知道自己 GPA/语言/科研背景能申到什么层次的学校，缺乏同背景案例参考。
- **文书没有参照**：PS/SOP/CV 怎么写、突出什么、避坑什么，缺少可溯源的范文与结构参考。
- **决策周期长**：学生往往需要反复搜索、对比、记录，容易遗漏 deadline 或 mismatched 项目。

### 1.2 价值

| 维度 | 传统方式 | StudyPath |
|------|---------|--------------|
| 信息搜集成本 | 人工翻阅多个官网/论坛，数小时 | 自然语言一句话提问，秒级召回 |
| 选校匹配效率 | 靠经验/中介，主观性强 | RAG 基于真实录取案例做背景对标 |
| 文书准备效率 | 无范文参照，从零写 | 检索范文库，给出结构与避坑建议 |
| 决策可靠性 | 容易记错 deadline/要求 | 每条信息都带 `source_url`，可点击核验 |

**核心落点**：用 RAG + 多智能体把留学申请的信息检索、选校匹配、文书准备三个高频环节自动化，降低学生时间成本，提升决策质量。

## 二、核心功能清单

### 2.1 RAG 问答系统

- **三库检索**：院校项目库（100 条）、录取案例库（50 条）、文书范例库（30 条），合计 180 条真实记录。
- **别名归一化**：支持 "CMU/帝国理工/港大" 等 38 所学校的中英文口语化简称，先归一再检索，提升召回率。
- **MMR 检索策略**：先按余弦相似度粗捞 20 条，再用 MMR 精挑 8 条，兼顾相关性与多样性。
- **来源可追溯**：每条检索结果都来自真实 `source_url`，驾驶舱底部以参考来源卡片形式列出，可点击核验。

### 2.2 LangGraph 多智能体框架调度

- **Supervisor（调度器）**：LLM 判断用户问题需要哪些领域专家，动态路由到对应 Worker。
- **三个领域专家 Worker（不是并列检索框，而是各有业务人设）**：
  - `school`（选校策略师）：接收用户画像，做硬性条件过滤 + 语义匹配，输出冲刺 / 稳妥 / 保底三档院校及匹配理由。
  - `admission`（录取风险评估师）：以候选校 + 用户背景为输入，对比真实录取 / 拒信案例，输出竞争力定位、风险点与补齐建议。
  - `essay`（文书规划师）：检索同方向优秀文书并拆解结构，输出文书大纲、段落要点与素材清单。
- **Synthesizer（综合器）**：消费三个 Worker 的结构化结论，去重、统一编号、按时间轴整合为五阶段申请规划（选校定稿 → 材料准备 → 文书写作 → 网申提交 → 面试准备）。
- **当前实现**：三个 Worker 并行执行（挂在 supervisor 同一条出边上，同一 superstep 并发 fan-out，fan-in 汇合到 Synthesizer）；各 Worker 只写专属 State 字段（school_* / admission_* / essay_*），无同 key 竞态、无需 reducer。实测见 `rag/test_parallel_topology.py`（假 LLM 计时：端到端 ≈ 3s，串行版 ≈ 5s）。

### 2.3 学术驾驶舱（Gradio 前端）

- **Profile Snapshot**：从用户 query 自动抽取 GPA、语言成绩、科研/实习、目标国家/专业/学校。
- **Fit 分析**：根据画像与检索到的项目要求做匹配度评估。
- **多维展示**：推荐结果、申请路线图、院校地图、申请策略建议。
- **路由可视化**：显示 Supervisor 派了哪些 Worker，让系统决策可解释。
- **参考来源卡片**：底部列出可点击的真实来源链接，多库来源全局统一编号（避免各 worker 各自编号导致答案引用与来源卡片对不上）。

### 2.4 Dify 低代码 MVP

- 在 Dify 上发布了一个独立的留学问答 Chatbot（`https://udify.app/chatbot/901mFjtnF9VuaQXb`）。
- 验证同一知识库在低代码平台上的快速落地能力。

### 2.5 N8N 自动化工作流

- 本地 Docker 部署 N8N。
- 实现 HTTP Request 调用 Dify API，形成"输入问题 → 调用 Dify → 返回结果"的自动化闭环。
- 可用于后续扩展：定时提醒、材料清单推送、新数据自动入库。

### 2.6 LoRA 领域微调

- 目标：让基座学会留学顾问的**表达范式**（文书语体、结构化输出、主动标注来源的习惯）。
- 方案：LoRA rank=8 / alpha=16 / target=q,k,v,o_proj，学习率 2e-4，3 个 epoch，batch=1 × grad_accum=8，bf16 + FlashAttention2。
- 数据：由 `annotations/build_sft_data.py` 从《院校数据采集.xlsx》三库构造 180 条 SFT（train 144 / eval 36）；训练时按 `val_size=0.1` 切分为 **129 训练 + 15 验证监控**。
- 环境：AutoDL RTX 3090 单卡 24GB，纯训练 **106.83 秒**（51 steps），train_loss 1.2952 → eval_loss 0.7597，收敛未过拟合。
- 产物：`model/lora/adapter_model.safetensors`（约 20MB）+ 两张 loss 曲线。
- **A/B 对照取证**（`finetune/ab_compare.py`）：同 prompt、同基座、greedy 解码，唯一变量是是否挂载 adapter —— 3/3 组业务任务输出发生行为改变，文书类从泛化陈述句转为第一人称文书语体。
- **客观评估**（`finetune/evaluate.py`）：20 条自动评估，指令遵循率 **100.0%**，平均 ROUGE-L **0.5731**。
- **能力边界核查**（`finetune/fact_audit.py`）：生成文本的来源 URL 对知识库真实 URL 白名单溯源命中率 **0/20**、排名数字一致率 **0/7** → 微调习得的是表达范式而非事实记忆，事实与溯源由 RAG 层负责。
- **应用层推理入口**：`finetune/inference.py::generate_essay()`（需基座在位；本地 4GB 显存无法加载 7B 基座）。

## 三、技术栈

| 层级 | 技术 |
|------|------|
| 大模型 API | DashScope qwen-plus（走 OpenAI 兼容端点） |
| 嵌入模型 | DashScope text-embedding-v3 |
| 向量库 | Chroma（本地持久化） |
| RAG 框架 | LangChain + 自实现 `DashScopeEmbeddings`（走原生 SDK 避兼容层 400） |
| 多智能体编排 | LangGraph StateGraph，手写 Supervisor-Worker-Synthesizer |
| 前端 | Gradio 4.x，自实现学术驾驶舱 UI |
| 低代码 MVP | Dify |
| 自动化工作流 | N8N（本地 Docker） |
| 微调框架 | LLaMA Factory + LoRA |
| 数据处理 | openpyxl、pandas |

## 四、数据规模与来源

| 库 | 条数 | 字段示例 | 来源要求 |
|----|------|---------|---------|
| 院校项目库 | 100 | 学校、项目、GPA/托福/雅思/GRE、截止日期、学费、排名 | 每条必须带 `source_url` |
| 录取案例库 | 50 | 背景、录取结果、项目、年份 | 同上 |
| 文书范例库 | 30 | 文书类型、结构、亮点、避坑 | 同上 |
| **合计** | **180** | | **全部真实可溯源，禁止虚构** |

- 数据来源：学校官网、QS、USNews、一亩三分地等公开渠道，人工采集整理成 Excel。
- 别名表：38 所高频学校的中英文别名映射，解决口语化查询召回问题。

## 五、量化成果

### 5.1 检索与生成（RAG 链路）

| 指标 | 数值 | 说明 |
|------|------|------|
| 规范集 HitRate@8 / MRR | 100% / 1.000 | 50 道规范提问 |
| 对抗集 HitRate@8 | 100% | 15 道口语化/别名/模糊查询全部召回 |
| 对抗集 MRR | 0.933 | 首个相关文档平均排名 |
| 路由覆盖率 / 精确率 | 100% / 63.3% | 30 道路由测试；Supervisor 倾向多派保召回，宁可多查不可漏查 |
| 生成忠实度 | 100% | 10 条回答全部引用了正确的 `source_url` |
| 延迟 P50 / P95 | 2.67s / 9.04s（RAG）· 3.12s / 9.17s（多智能体） | n=10 / n=5 |

### 5.2 领域微调（LoRA 链路）

| 指标 | 数值 | 说明 |
|------|------|------|
| 训练步数 / 纯训练耗时 | 51 steps / 106.83s | AutoDL RTX 3090 单卡，bf16 + FlashAttention2 |
| train_loss → eval_loss | 1.2952 → 0.7597 | 收敛未过拟合 |
| 指令遵循率 / 平均 ROUGE-L | 100.0% / 0.5731 | 20 条自动评估 |
| A/B 对照 | 3 / 3 组行为改变 | `identical = false`，唯一变量 = 是否挂载 LoRA |
| 事实层可溯源率 | 0/20（URL）· 0/7（排名） | 微调不承担事实记忆 —— 双轨架构的实证依据 |
| 权重体积 | 约 20MB | `model/lora/adapter_model.safetensors` |

## 六、项目边界（做了什么 / 没做什么）

### 已做
- 基于真实 180 条留学数据构建 RAG 知识库。
- LangGraph 多智能体问答链路可运行。
- Gradio 学术驾驶舱可本地演示。
- Dify MVP 已发布、N8N 自动化链路已跑通。
- LoRA 权重已训练落盘，并完成 A/B 对照、双轨评估与事实层能力边界核查。
- 评测体系与量化指标已落地（检索五层评测 + 微调双轨评估 + 事实层核查脚本）。

### 未做（后续可扩展）
- 多模态 OCR 解析用户简历/成绩单（架构里可接入，当前未实现）。
- 自动化的申请 deadline 提醒与材料清单推送（N8N 可扩展）。
- 更重的 Rerank 模型（当前用 MMR，未接入独立 Rerank）。
- Worker 按需动态裁剪到「部分并行」（当前 supervisor 全量路由三路并行；可演进为 conditional_edges / Send API 按 query 类型只派子集）。
- 用户登录与会话历史持久化（当前单轮无状态）。

---

## 七、一句话总结

StudyPath 是一个面向留学申请场景的 **RAG + 多智能体规划助手**：用 180 条真实可溯源数据构建知识库，通过 LangGraph 调度三个领域专家 worker，在 Gradio 驾驶舱里提供画像分析、选校匹配、文书建议，并配套 Dify MVP、N8N 自动化、LoRA 微调三个模块，最终目标是降低学生留学申请的信息搜集与决策成本。
